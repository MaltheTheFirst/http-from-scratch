# HTTP From Scratch

A full-stack web engineering project built with Node.js and TypeScript to explore the abstractions behind modern web frameworks.

Instead of starting with Express, Fastify, Next.js, React, or an ORM, this project implements routing, middleware, request parsing, sessions, authentication, database access, static file serving, and browser-side rendering directly with Node.js and browser primitives.

The goal was not to implement HTTP or PostgreSQL at the wire-protocol level. The goal was to understand what application frameworks normally do on my behalf by rebuilding those abstractions manually.

## Why I Built This

I had already worked with larger TypeScript applications using frameworks, APIs, databases, queues, and other abstractions, but wanted a stronger understanding of the mechanics underneath them.

This project was therefore deliberately built with very few dependencies.

The main dependency outside Node.js itself is `pg`, which is used to communicate with PostgreSQL.

The project became an exercise in tracing an application end-to-end:

```text
Browser
   ↓
HTTP request
   ↓
Node.js HTTP server
   ↓
Middleware
   ↓
Router
   ↓
Route handler
   ↓
Validation
   ↓
SQL
   ↓
PostgreSQL
   ↓
HTTP response
   ↓
Browser JavaScript
   ↓
DOM
```

## Features

### HTTP and Routing

The server uses Node's built-in `node:http` module.

The router implements:

- Method and pathname matching
- Dynamic route parameters
- Query parameters
- `GET`
- `POST`
- `PATCH`
- `DELETE`
- `HEAD`
- `OPTIONS`
- `404 Not Found`
- `405 Method Not Allowed`
- `Allow` headers
- Async route handlers
- Central route error handling

For example:

```text
/users/:userId
```

is matched against:

```text
/users/42
```

and produces:

```ts
{
    userId: "42"
}
```

### Request Parsing and Validation

Request bodies are read directly from the Node.js request stream.

The project includes helpers for:

- Accumulating streamed request-body chunks
- Validating `Content-Type`
- Parsing JSON
- Returning structured parsing failures
- Treating parsed external data as `unknown`
- Runtime type narrowing
- Endpoint-specific validation

The distinction between parsing and validation is intentional:

```text
raw bytes
↓
body string
↓
valid JSON
↓
unknown
↓
runtime validation
↓
trusted application data
```

### Middleware

A small middleware runner was implemented manually.

Current middleware includes:

- Request logging
- Request timing
- Session loading

Middleware is composed using an async `next()` function:

```text
request
↓
logger
↓
timer
↓
session middleware
↓
route handler
↓
timer resumes
↓
logger resumes
```

This demonstrates the execution model commonly hidden behind framework middleware systems.

### Sessions and Authentication

The project implements a simple session system using:

- UUID session IDs
- An in-memory `Map`
- HTTP cookies
- `HttpOnly`
- `SameSite=Lax`
- Login
- Logout
- Per-request session context
- Authentication guards

Authenticated routes use a higher-order `requireAuth()` wrapper that narrows the request context from:

```ts
session: Session | undefined
```

to:

```ts
session: Session
```

before the protected handler is called.

### PostgreSQL

Database access is performed directly through `pg` and handwritten SQL.

Implemented database concepts include:

- Connection pooling
- Environment-based configuration
- Parameterized queries
- `CREATE TABLE`
- `SELECT`
- `INSERT`
- `UPDATE`
- `DELETE`
- `RETURNING`
- Generated identity columns
- Primary keys
- Foreign keys
- Unique constraints
- Generated columns
- Constraint violations
- `JOIN`
- `ON DELETE CASCADE`
- Transactions
- `BEGIN`
- `COMMIT`
- `ROLLBACK`

Queries use PostgreSQL parameters instead of interpolating user input:

```sql
SELECT id, username
FROM users
WHERE id = $1;
```

with the runtime value supplied separately.

### Case-Insensitive Usernames

The database preserves the username as entered by the user while maintaining a generated normalized form:

```text
username:             Sebastian
username_normalised:  sebastian
```

The normalized column is generated by PostgreSQL:

```sql
username_normalised TEXT
    GENERATED ALWAYS AS (LOWER(username)) STORED
    UNIQUE
```

This means:

```text
Sebastian
sebastian
SEBASTIAN
```

represent the same logical username while the original capitalization remains available for display.

PostgreSQL unique-constraint violations are mapped to HTTP `409 Conflict`.

### Relational Data

The project contains two related tables:

```text
users
├── id
├── username
└── username_normalised

notes
├── id
├── user_id
└── content
```

`notes.user_id` references `users.id`:

```text
users.id
   │
   └──────► notes.user_id
```

Notes are considered dependent on their user, so the foreign key uses:

```sql
ON DELETE CASCADE
```

Deleting a user therefore also deletes that user's notes.

A relational query combines the two tables:

```sql
SELECT
    notes.id,
    users.username,
    notes.content
FROM notes
JOIN users
    ON notes.user_id = users.id;
```

The result is exposed through `GET /notes` and rendered by the browser.

### Transactions

`POST /users-with-note` demonstrates an atomic multi-step database operation.

The endpoint:

```text
BEGIN
↓
INSERT user
↓
receive generated user ID
↓
INSERT note using that ID
↓
COMMIT
```

If either insert fails:

```text
error
↓
ROLLBACK
```

Both operations therefore succeed together or neither is persisted.

A dedicated PostgreSQL client is acquired from the connection pool so the entire transaction stays on the same database connection.

### Static File Serving

Static files are served manually from the `public/` directory.

The implementation includes:

- Asynchronous filesystem access
- Path resolution
- MIME-type selection
- Static fallback routing
- `GET` and `HEAD` behavior
- Missing-file handling
- Directory traversal protection

For example:

```text
GET /styles.css
↓
resolve public/styles.css
↓
verify path remains inside public/
↓
determine Content-Type
↓
read file
↓
send response
```

### Browser Client

The frontend is written using native browser APIs rather than a frontend framework.

It implements:

- Form submission
- Event listeners
- `preventDefault()`
- `fetch`
- JSON serialization
- JSON response parsing
- DOM queries
- Dynamic element creation
- Collection rendering
- Delete buttons created at runtime
- Re-fetching authoritative server state after mutations
- Loading states
- Empty states
- Error states
- Responsive CSS

The browser can currently:

- Create users
- Find a user by ID
- List users
- Delete users
- Display relational note data

For example, creating a user follows this complete path:

```text
form submit
↓
browser event handler
↓
JSON.stringify()
↓
POST /users
↓
router
↓
JSON parser
↓
runtime validation
↓
parameterized INSERT
↓
PostgreSQL
↓
JSON response
↓
response.json()
↓
DOM update
```

## Running Locally

Install dependencies:

```bash
npm install
```

Create a `.env` file:

```env
DATABASE_URL=postgresql://...
```

Compile the TypeScript:

```bash
npx tsc
```

Create and seed the database tables:

```bash
node --env-file=.env dist/db/setup.js
```

Start the server:

```bash
node --env-file=.env dist/server.js
```

Then open:

```text
http://localhost:3000
```

## Example Requests

Create a user:

```bash
curl -i -X POST http://localhost:3000/users \
  -H "Content-Type: application/json" \
  -d '{"username":"alice"}'
```

Update a user:

```bash
curl -i -X PATCH http://localhost:3000/users/1 \
  -H "Content-Type: application/json" \
  -d '{"username":"AliceUpdated"}'
```

Create a user and note atomically:

```bash
curl -i -X POST http://localhost:3000/users-with-note \
  -H "Content-Type: application/json" \
  -d '{"username":"daniel","note":"Created in the same transaction"}'
```

## What the Project Rebuilds

A useful way to view the project is as a manual implementation of responsibilities normally delegated to libraries and frameworks:

| Implemented here | Common abstraction |
| --- | --- |
| Route table and matcher | Framework router |
| Route parameters | Router parameter parsing |
| `readBody()` | Body parsing middleware |
| `readJsonBody()` | JSON request middleware |
| Middleware runner | Express/Koa-style middleware |
| Request context | Framework request context |
| `requireAuth()` | Authentication guard |
| Cookie/session handling | Session library |
| Handwritten SQL with `pg` | ORM/query abstraction |
| Static fallback | Static-file middleware |
| DOM manipulation | UI rendering framework |
| Manual re-fetch/render | State-driven rendering |

The purpose was not to argue against those abstractions. It was to understand their responsibilities well enough to use them deliberately.

## Key Takeaways

The largest lesson from the project was that a web application is a sequence of boundaries rather than one piece of code:

```text
transport
≠
parsing
≠
validation
≠
application logic
≠
persistence
≠
presentation
```

The same applies to trust:

```text
external request
↓
unknown data
↓
validation
↓
application values
↓
parameterized SQL
↓
database constraints
```

And to asynchronous work:

```text
request stream
filesystem I/O
database query
HTTP fetch
```

Each uses a different API, but each represents work whose result becomes available later without requiring the entire program to stop executing.

## Limitations

This is a learning project rather than a production web framework.

Some intentional limitations include:

- Sessions are stored in memory and disappear when the process restarts.
- Static files are currently read as UTF-8, so the static server is intended for text assets such as HTML, CSS, and JavaScript rather than arbitrary binary files.
- Runtime validation is handwritten rather than handled by a schema-validation library.
- Database setup is a simple script rather than a migration system.
- There is no automated test suite; behavior was exercised manually through the browser and HTTP requests.
- Authentication is intentionally minimal and exists to demonstrate sessions, cookies, middleware, and route protection rather than a production identity system.

## Scope

Despite the name, **HTTP From Scratch** does not implement TCP, HTTP parsing, TLS, PostgreSQL's wire protocol, cryptography, or a browser engine.

It deliberately builds on mature lower-level primitives:

- Node.js HTTP
- Node.js filesystem APIs
- Node.js cryptography
- PostgreSQL
- `pg`
- Browser networking and DOM APIs

"From scratch" refers to rebuilding the application-level abstractions normally provided by web frameworks.

## Outcome

The finished application can now be traced across the complete stack:

```text
browser interaction
↓
HTTP request
↓
middleware
↓
routing
↓
request parsing
↓
runtime validation
↓
application logic
↓
SQL
↓

↓
```

The project served as a bridge between using web-development abstractions and understanding how those abstractions are constructed.

The next stage is to build with higher-level frontend and full-stack frameworks while being able to map their behavior back to these underlying primitives.
